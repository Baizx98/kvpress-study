# 永久驱逐与计算冷块策略的必要性分析

## 1. 问题背景

在当前 `kvpress` 原型中，你已经实现了两类块级策略：

1. **永久驱逐**
   - 典型代表：`BlockWisePress`
   - 一旦某些块被判定为不重要，就直接从物理 KV cache 中删除

2. **计算冷块**
   - 典型代表：`DualPhasePerLayerPress` 的非永久驱逐模式
   - 所有 KV 在物理上保留
   - 但当前步只让一部分 `active blocks` 参与 attention 计算
   - 其余块暂时不参与计算，但后续可以重新变热并重新参与

从 Quest 的经验看，尤其是在 `decode` 阶段，KV 的重要性和当前 query 强相关。  
这意味着：

- **永久驱逐** 更像基于“当前时刻”做一次不可逆决策
- **计算冷块** 更像保留未来反悔空间的可逆决策

所以从理论上讲，在 query-dependent 很强的任务上：

- 关闭永久驱逐
- 打开计算稀疏

确实有可能获得更好的准确率表现。

但你最近在 `LongBench` 这类更贴近真实任务的数据集上观察到：

- `DualPhasePerLayerPress` 的非永久驱逐模式
- 和永久压缩版 `BlockWisePress`

结果非常接近，甚至略低一点。  
这说明“理论上更优”并不等于“当前实现里一定更优”，需要从更细的层面拆开分析。

---

## 2. 从准确度角度分析：为什么两类策略都需要

### 2.1 永久驱逐的优点

永久驱逐的最大优点是：

- 决策简单
- 行为稳定
- 训练外推理时更容易形成一致的缓存状态

在 `prefill` 后，如果某些块已经明显不重要，直接删除它们通常有几个好处：

1. **减少后续状态复杂度**
   - 后面的 decode 不需要继续在这些块上做状态维护
   - 块热度管理、mask 更新、分数刷新都更简单

2. **减少错误恢复开销**
   - 没有“这一轮不算、下一轮又算”的频繁状态波动
   - 算法行为更平稳

3. **更接近当前原型平台**
   - `kvpress` 的原生表达更适合“剪掉一段 token 索引后重写 cache”
   - 所以永久压缩在当前平台上实现得更自然

也正因为如此，在你当前的原型实现里，永久驱逐版 `BlockWisePress` 往往表现得更稳。

### 2.2 计算冷块的理论优势

计算冷块真正的优势，主要出现在 **decode query 强依赖** 的任务上。

这里有一个关键区别：

- `prefill` 阶段的 question-aware 评分，本质上还是“用问题末尾的一段 query”去预估未来重要块
- 但在 `decode` 阶段，模型每生成一个新 token，query 都在变化
- 因此块的重要性不是静态的，而是动态变化的

这时候，如果前面把某个块永久删掉，就会出现一种风险：

- 这个块在当前时刻不重要
- 但未来某一步 query 可能又需要它
- 一旦它已被永久删除，就没有恢复空间

而计算冷块策略的优势就在于：

- 当前步先不让它参与计算
- 但物理上还留着
- 后续 query 变了，重新判定它又重要时，可以再让它回来

也就是说，**计算冷块用额外的状态复杂度，换来了 query-aware 恢复能力**。

### 2.3 为什么在 LongBench 上二者差异不大

你最近的实验里，`LongBench` 上非永久驱逐和永久驱逐结果接近，这并不矛盾。

更可能的原因是：

1. **这些任务的答案生成通常不长**
   - decode 阶段的 query 演化空间有限
   - 也就是说，后续“翻案”的机会不多

2. **主要信息需求在 prefill 后已经基本确定**
   - 如果 prefill 末尾的问题 query 已经能较好识别关键块
   - 那么永久驱逐和非永久驱逐的差距就不会太大

3. **当前 `DualPhasePerLayerPress` 还不是为精度最优专门设计的**
   - 它更像一个块状态管理器
   - 而不是一条极致优化后的 query-aware 解码路径

所以当前观察到的结论更合理地表述为：

- 在以 `LongBench` 为代表的真实长文 QA 任务上
- 永久驱逐已经足够有效
- 非永久驱逐暂时没有显著展现出精度优势

### 2.4 为什么在 RULER / Needle / 更强检索型任务上可能出现差异

像 `RULER` 这类任务，尤其是：

- `niah_single_3`
- `niah_multikey_2`
- `niah_multikey_3`

它们更接近下面这种模式：

- 远距离证据块非常稀疏
- 支持块数量可能不止一个
- 某个块当前步不重要，不代表后续所有步都不重要

这时，永久驱逐更容易暴露两个问题：

1. **误删未来可能重新变热的块**
2. **多支持块任务中，某些“当前次热点块”被删后无法恢复**

而计算冷块在这些任务里理论上更有价值，因为它允许：

- 当前只算最热块
- 但把一部分潜在支持块先留在物理缓存里
- 等 query 变化后再重新激活

因此，**从准确度角度看，这两类策略不是互相替代的，而是面向不同 query 动态性的两种机制**：

- 永久驱逐适合“未来重要性相对稳定”的场景
- 计算冷块适合“未来重要性可能反复变化”的场景

## 3. 从未来卸载框架角度分析：为什么计算冷块更重要

如果站在你未来要做的 **GPU-CPU 两级块卸载系统** 的角度，这个问题就更清楚了。

### 3.1 永久驱逐适合作为“容量回收机制”

永久驱逐最适合解决的是：

- 这部分块以后大概率都不再需要
- 那就直接从系统里回收掉

它天然承担的是：

- **释放物理显存**
- **缩小后续缓存规模**
- **减少未来状态维护成本**

所以在卸载系统里，永久驱逐对应的角色更像：

- 真正的垃圾回收
- 真正的不可逆容量回收

### 3.2 计算冷块适合作为“在线调度机制”

而计算冷块更适合承担的是：

- 当前步先不参与计算
- 但不代表以后完全没用

所以它天然对应卸载系统中的这些动作：

1. **GPU 常驻但不参与当前计算**
   - 对应 `resident_gpu`

2. **逻辑冷块，可下沉到 CPU**
   - 对应 `offloaded_cpu`

3. **未来可能重新变热，需要预取**
   - 对应 `prefetch_to_gpu`

也就是说，计算冷块天然就是一个：

- **调度状态**
- **热度状态**
- **预取状态**

它和卸载系统的契合度比永久驱逐更高。

### 3.3 为什么卸载框架里必须同时保留两类机制

如果系统里只有永久驱逐，没有计算冷块，会有两个问题：

1. **太激进**
   - 一旦删错就无法恢复
   - 对 query-aware 动态变化不友好

2. **无法自然表达“暂时不需要，但以后可能需要”**
   - 这恰恰是 GPU-CPU 两级存储最常见的状态

如果系统里只有计算冷块，没有永久驱逐，也有问题：

1. **显存和 CPU 容量回收不彻底**
   - 所有块都永远存在，只是状态不同
   - 长时间运行后系统压力仍会积累

2. **状态管理成本更高**
   - 需要长期维护更多块的元信息和冷热判断

因此，对未来卸载系统来说，更合理的设计一定是：

- **永久驱逐**：负责真正回收“长期冷、近乎不再需要”的块
- **计算冷块**：负责在线调度“当前冷、未来可能再热”的块

这两者不是二选一，而是应该同时存在。

## 4. 对你当前研究路线的启发

### 4.1 当前阶段：永久驱逐仍然是算法验证主线

在当前原型阶段，你更关心的是：

- `BlockWisePress` 的块重要性评分是否靠谱
- 永久压缩后精度是否还能稳定

那么永久驱逐依然是最合适的主线，因为：

- 实现更简单
- 行为更稳定
- 更容易和 `ChunkKV` 做公平对比

### 4.2 下一阶段：计算冷块更适合作为系统主线

当你开始真正写块级卸载推理框架时，计算冷块的重要性会明显提升。

因为那时你要解决的就不只是“保不保留这个块”，而是：

- 这个块现在参与不参与计算
- 它现在在 GPU 还是 CPU
- 未来几步需不需要预取
- 它是永久删掉还是只是暂时冷却

这些问题本质上都更接近 `DualPhasePerLayerPress` 现在表达的那套状态机。

### 4.3 论文叙事上怎么讲

如果以后要把故事讲完整，我建议这样分工：

1. **BlockWisePress**
   - 负责证明：块摘要 + query-aware 评分可以在真实任务上保持较好精度

2. **DualPhasePerLayerPress**
   - 负责证明：块不仅能被压缩，还能被动态调度
   - 支撑未来的“参与计算 / 驻留 GPU / 卸载 CPU / 预取 / 永久删除”统一块状态管理

3. **最终卸载框架**
   - 负责把这两类动作统一起来：
     - 永久驱逐做容量回收
     - 计算冷块做在线调度

这样你的系统故事会更完整，也更符合 systems 论文的表达方式。

---

## 5. 当前可以得出的阶段性结论

从准确度角度：

- 永久驱逐并不一定比计算冷块差
- 在真实长文 QA 任务上，它已经足够稳
- 但在更强 query-dynamic 的检索任务上，计算冷块理论上更有潜力

从未来卸载框架角度：

- 永久驱逐是“容量回收机制”
- 计算冷块是“在线调度机制”
- 两者都必要，而且承担的角色不同

因此，对你的系统最终形态来说，最合理的路线不是“二选一”，而是：

- 当前用永久驱逐验证评分算法
- 后续用计算冷块承接块状态管理和卸载调度
